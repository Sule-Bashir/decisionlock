## The Problem
AI coding assistants have a memory problem.
You tell the AI:
> "Don't use Firebase. We're using PostgreSQL."
Twenty prompts later, it suggests Firebase again.
Or you say:
> "Our API must never expose user emails."
Later, it generates an endpoint that returns them.
The problem is not that AI cannot generate code. The problem is that **AI forgets the project's decisions and constraints**. Every session starts fresh. Every prompt is treated in isolation. The developer becomes the only thing holding the project's rules together.
This leads to:
- Repeated mistakes the developer already corrected
- Inconsistent architecture across files
- Security rules that get silently violated
- Code that "works" but the developer cannot explain or trust
## What DecisionLock Does
DecisionLock is a project memory firewall for AI-assisted development.
It stores the decisions a project has committed to, then scans AI-generated output against those decisions before the developer accepts it.
The core loop is four steps:
1. Record decisions — Create a project and add its rules (e.g., "Use PostgreSQL," "Never expose user data").
2. Paste AI output — Drop in code or text generated by any AI assistant.
3. Scan for violations — DecisionLock checks the output against every rule and returns a compliance score plus a list of conflicts.
4. Fix with AI— One click produces a corrected version that respects every decision.
Every violation includes:
- The rule that was broken
- A risk level (low / medium / high)
- A plain-language explanation
- A concrete suggested fix

## How It Works
### 1. Create a project
A project is a container for decisions. It has a name, a description, and a list of rules.
### 2. Add rules
Each rule has:
- text— the decision itself (e.g., "Never use Firebase")
- category — `technology`, `security`, or `process`
- importance — `low`, `medium`, or `critical`
### 3. Scan AI output
The backend builds a prompt containing:
- The full list of project rules, numbered and tagged with importance
- The pasted AI output
It sends this to the Groq API and asks for a strict JSON response:
```json
{
  "complianceScore": 0,
  "satisfied": [],
  "violations": [
    {
      "ruleNumber": 1,
      "risk": "high",
      "explanation": "The code uses Firebase Firestore, which is explicitly prohibited.",
      "suggestedFix": "Replace Firebase with a PostgreSQL client such as pg.",
      "ruleText": "Never use Firebase"
    }
  ]
}
The backend attaches the full rule text to each violation before returning it to the frontend.
### 4. Fix violations
The fix endpoint sends:
- The original AI output
- The list of detected violations
It asks the model to rewrite the output so it respects every rule, and returns only the corrected text.

Why curl instead of Node's native fetch?
Node.js's built-in `fetch` (undici) does not reliably honor DNS and proxy settings in restricted environments such as Termux on Android. The backend uses `child_process.execFileSync` to call the system `curl` binary, which follows the operating system's network configuration correctly.

## API Reference
Base URL (production): `https://decisionlock.onrender.com`
### `GET /`
Health check.
Response:
```json
{ "status": "ok", "service": "decisionlock-backend" }
### `POST /api/projects`
Create a new project.
Body:
```json
{ "name": "AgentPay", "description": "Demo project" }
Response:
```json
{
  "id": "pb6vfb4r",
  "name": "AgentPay",
  "description": "Demo project",
  "rules": [],
  "createdAt": "2026-10-06T10:11:01.000Z"
}
### `GET /api/projects/:id`
Fetch a project with its rules.
Response:
```json
{
  "id": "pb6vfb4r",
  "name": "AgentPay",
  "rules": [
    { "id": "l7njrb1t", "text": "Never use Firebase", "category": "technology", "importance": "critical" }
  ]
}
### `POST /api/projects/:id/rules`
Add a rule to a project.
Body:
```json
{
  "text": "Never use Firebase",
  "category": "technology",
  "importance": "critical"
}
Response:
```json
{ "id": "l7njrb1t", "text": "Never use Firebase", "category": "technology", "importance": "critical" }
### `POST /api/projects/:id/scan`
Scan AI-generated output against the project's rules.
Body:
```json
{ "inputText": "const db = firebase.firestore();" }
Response:
```json
{
  "complianceScore": 0,
  "satisfied": [],
  "violations": [
    {
      "ruleNumber": 1,
      "risk": "high",
      "explanation": "The code imports and uses Firebase Firestore, which is explicitly prohibited.",
      "suggestedFix": "Remove Firebase and use PostgreSQL instead.",
      "ruleText": "Never use Firebase"
    }
  ]
}
### `POST /api/projects/:id/fix`
Generate a corrected version of the AI output.
Body:
```json
{
  "inputText": "const db = firebase.firestore();",
  "violations": [
    { "ruleText": "Never use Firebase", "explanation": "Firebase is used." }
  ]
}
Response:
```json
{
  "fixedText": "const { Pool } = require('pg');\nconst db = new Pool({ connectionString: process.env.DATABASE_URL });"
}
## Local Development
### Prerequisites
- Node.js 18 or later
- Git
- A Groq API key ([console.groq.com/keys](https://console.groq.com/keys))
### 1. Clone the repo
```bash
git clone https://github.com/Sule-Bashir/decisionlock.git
cd decisionlock
### 2. Set up the backend
```bash
cd backend
npm install
Create `.env`:
```bash
cat > .env << 'ENVEOF'
GROQ_API_KEY=your-groq-key-here
GROQ_MODEL=openai/gpt-oss-120b
PORT=3001
ENVEOF
Start the backend:
```bash
node server.js
You should see:
DecisionLock backend listening on port 3001
### 3. Set up the frontend
In a second terminal:
```bash
cd frontend
npm install
Create `.env.local`:
```bash
cat > .env.local << 'ENVEOF'
NEXT_PUBLIC_API_URL=http://localhost:3001
ENVEOF
Start the frontend:
```bash
npm run dev
Open [http://localhost:3000](http://localhost:3000).
Note: On Termux/Android, `next dev` may fail because `@next/swc-android-arm64` does not exist on npm. In that case, deploy the frontend to Vercel and only run the backend locally. This is the approach used for this project.
### 4. Test the API directly

## Deployment
### Backend → Render
1. Go to [render.com](https://render.com) → New→ Web Service
2. Connect the `Sule-Bashir/decisionlock` repo
3. Configure:
   - Root Directory: `backend`
   - Runtime: Node
   - Build Command: `npm install`
   - Start Command: `node server.js`
   - Instance Type: Free
4. Add environment variables:
   - `GROQ_API_KEY` = your Groq key
   - `GROQ_MODEL` = `openai/gpt-oss-120b`
5. Deploy
### Frontend → Vercel
1. Go to [vercel.com](https://vercel.com) → Add New → Project
2. Import the `Sule-Bashir/decisionlock` repo
3. Set Root Directory to `frontend`
4. Add environment variable:
   - `NEXT_PUBLIC_API_URL` = `https://decisionlock.onrender.com`
5. Deploy
Important: When Vercel detects both `backend/` and `frontend/`, it may offer to import the repo as a multi-service project. Do **not** do this. Set the Root Directory to `frontend` so Vercel only builds the Next.js app. The backend is already on Render.
## Demo Flow
The 90-second demo tells a story:
1. Landing page — "AI coding assistants forget decisions you already made."
2. Launch live demo — creates the AgentPay project with four rules.
3. Dashboard — shows the Project Guard:
   - Use PostgreSQL for the database.
   - Never use Firebase.
   - Never expose private user data.
   - Payments must require human confirmation.
4.Paste AI output — pre-filled with code that uses Firebase, returns user emails, and processes payments automatically.
5.Scan— 0% compliance,4 conflicts detected, each with risk level, explanation, and suggested fix.
6.Fix— one click produces PostgreSQL code that:
   - Uses `pg` instead of Firebase
   - Only returns non-sensitive fields (`name`, not `email`)
   - Creates payments with `status: 'pending'` requiring human confirmation
7.Closing line — "DecisionLock. AI remembers what you decided — not just what you asked."
## Roadmap
The current version is a proof of concept. Planned improvements:
- Persistence — Replace the in-memory store with a database (PostgreSQL, naturally).
- Decision history — Track when rules were added and which AI outputs violated them.
- Risk intelligence — Weight rules by importance and block high-risk outputs automatically.
- IDE integration — Scan AI output directly inside the editor.
- Multi-project support — Manage rules across multiple repositories.
- Authentication — Per-user projects and rule sets.
- Export/import — Share rule sets between developers.
